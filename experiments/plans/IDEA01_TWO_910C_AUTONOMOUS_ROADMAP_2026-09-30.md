## 1. 研究要交付什么

**C1（主问题）**：冻结的文本条件 CAD 生成器，对已有 CAD 原生表示的条件分数，能否把 Text2CAD 登记配对 UID 排到图库前列？主协议 A 是官方 v1.0 test 的 8,046 个 CAD、7,934 条非空 L0 查询；主指标 R@1/5/10/20、MedR、覆盖率和置信区间。它们是**登记 UID 检索**指标；逐字重复查询对应不同 UID，不能把单正例命中率解释成全部语义相关 CAD 的召回率。

**C2（机制与边界）**：观测到的排序有多少来自文本条件，有多少可由候选的无条件先验、长度、代码词面、表示缺失或训练交叉解释？最低证据是同一候选的有/无查询分数、`S(q,C)` 与事前固定的 `S(q,C)-S(∅,C)`、不使用配对文本的词面/长度基线、固定 split 的泄漏和失败样本审计。正结果和负结果都交付原始分数；不把先验校正称为新方法。

核心实验块不超过四项：B1 数据与评分仪器；B2 同图库登记 UID 排序；B3 无条件先验和捷径诊断；B4 失败与几何等价抽查。B1–B3 是必做，B4 的自动几何审计必做，人工语义判定若没有独立标注来源则只列未完成的主张。HoLa/STEP 等 B-rep 路线先做可行性门，不能让其资产/移植问题阻塞前三臂。

## 2. 计算事实与结论边界

- M0 已审：CADmium 原生 JSON、官方命令向量均覆盖 8,046 个 test UID；CADmium train/validation 与官方 test 精确 UID 无交叉。Text-to-CadQuery 训练 UID 与官方 test 交叉 4,581，因此它只进入独立定义的干净子集 C，不能把 A 全集成绩称为 held-out。家族级近重复尚未排除。
- M1a 已审：CADmium 的 CPU 评分边界、tokenizer 模板和合成 logits 测试通过；真实 LoRA/基座加载、NPU 前向、吞吐和 `IMPLEMENTATION.md` 均未交付。当前 `ACTIVE_TASK.md` 的 `approved_sha=无`、NPU 预算为零。
- 7,934 条查询只有 3,644 种 `strip()` 后的文本；同文本、同模型提示必有相同分数行，允许**仅按查询文本无损去重计算，再按冻结 query 清单还原**。因此完整 A 矩阵需要 3,644×8,046＝29,319,624 个唯一评分对，而不是 63,836,964 次前向；指标仍以 7,934 条原始查询计算。去重器不能读取 qrels。
- 历史 CadQuery P1 的约 0.52 秒/对只提示风险，不可外推 CADmium。若新模型实测仍是 0.52 秒/对，两个卡一直满载的 A 穷举约需 **88 天**；即使有效速度到 0.05 秒/对，仍需约 8.5 天。为在 7 天内做完 A 穷举，两卡各自的含批处理有效耗时须不高于约 **0.041 秒/对**。此预算由真实长度分布、批量和 checkpoint 的测量重算，不能用短样本的 10 对计时宣称全库可行。
- “100 条查询×完整 8,046 图库”是真全图库、抽样查询实验；“全部查询×固定短名单后生成器重排”是两阶段系统。两者和完整 A 穷举必须分别命名、分别报告，且均不是本轮全量必交付的替代品。短名单不得强行塞入真 UID。

## 4. 分阶段自动执行合同

每个阶段都按“Codex 写子合同与上限 → 本地 Claude Code（当前为 **Kimi K3 官方 API**）只做该合同 → Kimi 本地提交/推送并回填 → Codex 审码 → Codex 将完整 `approved_sha`、卡数、对数、墙钟写入 `ACTIVE_TASK.md` → 服务器只 fetch/detach/run → Kimi 回填原始结果 → Codex 独立核验并决定下一阶段”循环。不要把“自动”理解为跳过 Codex 审核；常规通过可自动进入下一门，超出预算或改变科学口径时停下向用户报告。

| 门 | 产物和核验 | 资源上限与自动流转 |
|---|---|
| G0：补完 M1a | Kimi 本地实现 CADmium 真实 LoRA 载入和 NPU runner；独立重算 7,934×8,046 长度/覆盖；检查全部小型配置、M0 query/gallery/qrels 清单的本地运行副本；交 `IMPLEMENTATION.md`、测试、完整 SHA、准确命令和内存估计 | 0 NPU；Codex 审查输入隔离、shift/EOS、指纹、截断、预算台账及运行环境。失败留 `BLOCKERS.md` |
| G1：真实评分烟测 | 每臂先 1 对，再覆盖短/长/边界的 10 对；保存输入 token IDs、逐 token log-prob、sum/mean、非有限检查、HBM/时间和完整模型/数据 SHA；与独立索引计算核对 | 每次仅 1 卡；每臂至多 11 对、1 卡小时，须先获 SHA 批准。任何目标错位、非确定性超界、配置错配或 OOM 停止，不放大 |
| G2：吞吐与小池 | 事前固定的 100 query×100 candidate 池，另测覆盖实际 token 长度分位的 1,000 对；有条件/空查询、随机/长度/不含配对文本的原生词面基线；做批量/两卡**独立分片**吞吐测量 | 先 1 卡验证批量分数等价，再最多 2 卡；每臂上限 11,000 条条件对、相应至多 8,046 条无条件对；初始上限 24 卡小时，Codex 逐臂批准。小池仅 sanity，不写作全库 R@K |
| G3：真全图库代表性测速 | 只有 G2 的长度分层模型在加入 30% 余量后仍预测全量≤7 天，才固定 100 种代表性 query 文本，对该臂完整 8,046 候选进行**两卡稳态**评分；用真实 2.7% 左右的唯一评分矩阵、长尾长度及断点开销复核 ETA。另算该子集 UID R@K、覆盖率和 cluster CI | 单臂至多 144 卡小时、72 小时墙钟；若 G2 已预测超 7 天，停止在 G2 并讨论，不先花数天跑 G3；G3 测得实际吞吐不达标也停止，不静默缩小样本 |
| G4：正式全量 | **必须**完成去重的 3,644×8,046 精确全图库矩阵并恢复 7,934 条 query 的排名 | 只有 G2 与 G3 的**保守 ETA**均≤7 天、审查通过且完整 SHA/预算写入 `ACTIVE_TASK.md` 才自动启动；全量硬上限 168 小时墙钟、336 卡小时。若估计超 7 天或运行中超预算，保存可复用分片并停下讨论加速/时间，不把部分矩阵或短名单冒充完成 |
| G5：交付与复核 | Kimi 交原始逐对分数/失败、环境与 SHA、预算台账、指标脚本、结果事实/分析分开的 `RESULTS.md`；Codex 重算抽样/全量指标、审运行 SHA 和源码、查泄漏及错误案例，形成结论与下一步 | 无新 NPU。若证据不足则标 `inconclusive`，不填造缺项；通过后才可将阶段改 `reviewed` |

G2 之后的两卡任务按 query 或候选的稳定 hash 切成互斥分片，两个进程各绑定一张 NPU，各自按原子文件落盘；合并器核对 `(query_hash,cad_id,model_sha,score_spec_sha)` 恰好一次、排序无关、无缺行/重行。跨断点重启只复用校验通过的分片，模型/数据/代码/配置 SHA 变动则生成新 run，不混分数。多卡不是 DDP；若两卡之一被他人使用或健康异常，自动降到一张并重估 ETA，超过获批墙钟门槛则停止并报告，不能把部分矩阵充作完整结果。

## 5. 评分、统计和止损的固定口径

1. 正式评分层只读 query 文本、单个候选的固定原生目标、公开且固定的提示及模型文件；qrels、CADmium `annotation`、原 CSV 和匹配 UID 不能进入分数函数。候选排序和短名单选择不能看 qrels。数据审计与评价进程可读取 qrels。
2. CADmium 以原作者模板的完整 assistant 目标（含 `<|im_end|>` 和换行）算 `S_sum`；CadQuery 用其官方完整程序加 EOS；原版 Text2CAD 须先证明多头联合目标的计算定义。`S_mean` 只作长度诊断。`S(∅,C)` 每候选至多算一次，α=0（原分数）与 α=1（已知先验校正）事前固定；其它 α 只能在 validation 冻结后作为次级分析。
3. CADmium 已初测部分对超过 4096 token；runner 必须独立普查、拒绝截断。不可评分候选留在 8,046 图库，在排名时统一置于可评分候选之后，配对 UID 不可评分计未命中；同时给“目标可评分查询子集”的条件指标及整体覆盖率。相同分数使用与 qrels 无关的稳定 CAD ID hash 破平，另报严格无并列命中率；不因模型失败缩小分母。
4. 100-query 全图库子集在看任何该模型 test 分数前固定；样本置信区间以**相同规范化文本为 cluster** 重采样，另报按官方 query 频数加权和按唯一文本等权两套视角。全量 A 的 45.93% 单正例 R@1 理论上限要随表列出；统计检验先算成对差值，再决定是否可以说优于基线。
5. 至少保留随机、长度/复杂度、字符/符号词面三个基线族；词面不得读配对 caption。短名单的一阶段训练若使用配对数据，必须单列为“含外部对齐”的系统，不能和无额外训练的主张混为一体。几何编译/拓扑近似可自动筛出“登记错、语义可能对”的案例，但不能单凭 Chamfer 或 token 相似度改写语义 qrels。
6. 停门：资产 SHA/许可不明；训练交叉或家族泄漏未标注；评分目标错位/截断；成对分数与 query 无关；基线/先验足以解释全部结果且没有新增问题；候选转换覆盖过低；预估/实际资源超限；run 台账无法对齐 SHA；或自动重试仍同样失败。每一项保留失败证据并停在受影响的臂，其它独立臂可继续。

## 6. 全自动协作、归档与异常处理

- **本地** `D:\projects\IdeaSpark\CADRetrievalIdea1` 是唯一源码与计划编辑位置；Kimi 通过 Claude Code 只读 `CLAUDE.md`→`ACTIVE_TASK.md`→当前子合同，写 `experiments/src|scripts|configs|tests` 和自己的 `experiments/submissions/<task_id>/`。Codex 写计划、审核、改状态。Kimi 官方 API 无响应/额度/上下文中断时，先落盘当前进展和调用错误，不自动改用其他模型或复述失去上下文的任务；Codex 重新分配短任务。
- 本地提交并推送 `origin`，云脑 `/home/ma-user/work/CADRetrieval` 只 `git fetch` 后检出**被 Codex 批准的完整 SHA**运行；远端不能编辑/热补/提交项目文件。执行前后检查 `git status --porcelain`，运行目录 `/home/ma-user/work/CADRetrieval_runtime/runs/<run_id>/` 在 checkout 外。云脑 `/data/data_dev` 曾卡住，默认从本机运行副本读；重要结果再复制到共享 OBS `/data/obs_data_liuza/CADRetrieval/runs/` 并两端 SHA 核验，不依赖该卡住的挂载。
